# Workers용 grpc-js drop-in 교체 패키지 — 구현·API·호환성 상세 명세

**문서:** 제안 v0.3 / **기준일:** 2026-09-21 / **작업명:** `workers-grpc-adapter`  
**첫 제품 목표:** package.json alias·override와 소수의 부트스트랩 설정만 바꾸어 기존 `@google-cloud/datastore` 비즈니스 코드를 Cloudflare Workers에서 실행한다.  
**상태:** 설계 및 검증 자산 명세. 실제 교체 라이브러리, SDK 실행, Workers 배포, Google API E2E는 구현·검증하지 않았다. 동봉된 타입 선언은 제안한 확장 API이며 런타임 구현이 아니다. 코드·명령 예시의 **예상 결과**와 실제 수행한 문서·타입 검사 결과는 25장에서 분리한다.

이 문서는 v0.2를 대체하는 독립 명세다. `MUST/필수`, `MUST NOT/금지`는 구현 요구사항이며 이미 지원한다는 의미가 아니다. `계획`, `후보`, `미검증`은 호환 인증과 구분한다. 작업명과 `0.3.0`은 미배포 예시다. Datastore `10.1.0`은 검증 시작 후보이지 최신 버전 또는 실행 인증된 버전이 아니다.

## 읽는 순서

사용자 설치는 2장, 공개 API는 5–8장, transport 구현은 9–14장, Datastore의 추가 빌드 경로는 15장, 테스트·호환 인증은 17–23장을 따른다. 동봉 `compatibility/test-catalog.json`에는 테스트 ID·절차·예상 결과·증거·실행 계층을, `requirements.json`에는 요구사항 ID를 둔다. 카탈로그의 모든 구현 테스트는 현재 `planned / not_run`이다.

## 1. 제품 계약과 v0.3의 확정 결정

### 1.1 drop-in의 정확한 의미

다음 계약을 동시에 만족해야 drop-in으로 부른다.

| ID | 필수 계약 |
|---|---|
| R-001 | 루트 alias와 overrides가 앱 및 SDK의 모든 관련 GAX 의존 경로에서 replacement를 해석한다. |
| R-002 | 지원한 root/deep exports, ESM/CJS, 타입 및 클래스 identity를 보존한다. |
| R-003 | SDK import·생성자·비즈니스 호출·반환값 처리 코드는 native baseline과 동일하다. |
| R-004 | 실제 SDK의 정적 import·proto 초기화·인증·첫 호출까지 Workers에서 실행한다. |
| R-005 | grpc-js 생성 클라이언트와 사용자 인터셉터의 관찰 가능한 계약을 유지한다. |
| R-006 | Google 인증과 credentials composition을 연결하고 논리적 서비스의 audience를 유지한다. |
| R-007 | Unary와 server streaming을 incremental gRPC-Web로 처리한다. |
| R-008 | 상태 전이·취소·deadline·종료 정리가 결정적이며 최종 status와 write callback은 중복되지 않는다. |
| R-009 | 초기 metadata, trailing metadata, binary 값과 오류 상세를 보존한다. |
| R-010 | 응답 스트림의 backpressure와 메시지/헤더 예산을 준수한다. |
| R-011 | 어댑터는 한 Call에 대해 데이터 RPC fetch를 최대 한 번만 실행한다. |
| R-012 | Datastore CRUD·데이터 표현·Query·SDK object stream을 보존한다. |
| R-013 | Datastore transaction·쓰기 결과 불확실성·SDK 재시도 경계를 보존한다. |
| R-014 | endpoint·TLS·redirect·인증정보·요청 간 상태의 보안 경계를 지킨다. |
| R-015 | 비지원 API와 옵션은 명시적으로 실패하며 조용한 기능 축소를 하지 않는다. |
| R-016 | 필요한 빌드 변환은 고정한 SDK/GAX/schema 프로파일 안에서만 수행한다. |
| R-017 | 지원 버전·플랫폼은 실제 시험 행렬과 증거로 인증한다. |
| R-018 | 설치 tarball·exports·선언 파일·라이선스·패치가 재현 가능하다. |
| R-019 | 문서 예제는 소비자 fixture에서 추출하고 문서와 실행 상태를 일치시킨다. |
| R-020 | 소유 버퍼·번들·cold initialization·stream 성능을 측정하고 회귀를 기록한다. |

### 1.2 바꾸어도 되는 것과 안 되는 것

**허용:** 루트 dependency 설정, Worker entrypoint, 명시적 서비스 계정 credentials 공급, runtime compatibility 설정, 필요할 때 공식 Datastore 빌드 프리셋 한 곳. 앱 자체의 권한 검증과 안전한 HTTP 오류 응답도 부트스트랩 책임이다.

**금지:** SDK import 변경, 각 SDK에 `gaxOptions()` 강제, `options.grpc`/`channelFactoryOverride` 수동 삽입, REST fallback 활성화로 성공 처리, 수동 node_modules 수정, 무조건적인 `skipLibCheck`, `as any`, 런타임의 임의 eval 허용. 앱의 기존 native gRPC 연결 설정·mTLS·파일 경로 ADC까지 무조건 동일하다고 약속하지 않는다.

**동일 코드의 단위:** `fixtures/shared/datastore-business.ts`의 bytes와 SHA-256을 기준으로 한다. 인증 객체를 만드는 entrypoint는 환경별로 달라도 된다. 환경별 서로 다른 비즈니스 함수를 만들어 결과만 비교하는 것은 불합격이다.

### 1.3 v0.2에서 더 구체화하거나 수정한 결정

| 주제 | v0.3 결정 |
|---|---|
| 기본 Channel 연결 | 공개 Client만 감싸지 않고 vendored client 생성·interceptor의 하단 bridge를 함께 변경한다. |
| RPC 종류 전달 | alias 경로는 user invocation transformer를 덮어쓰지 않는다. 최종 메서드 정의·CallOptions가 모인 내부 bridge에서 전달한다. |
| Deadline 기본값 | 명시한 `Infinity`와 생략된 deadline을 구분한다. Infinity를 패키지 기본 timeout으로 대체하지 않는다. |
| 인증 오류 | 모든 생성 실패를 UNAUTHENTICATED로 통일하지 않는다. 고정 upstream의 control-plane status 정책을 따른다. |
| Unary 이벤트 | callback 오류와 `status` 이벤트를 분리하여 비교한다. 둘의 code가 항상 같다고 가정하지 않는다. |
| Metadata | `getMap()`만 사용하지 않는다. 이 API는 복수 값 전송용이 아니다. |
| Proto 초기화 | 정적 JSON만으로 runtime code generation 문제가 해결된다고 보지 않는다. ctor·codec·reflection 경로를 함께 확인한다. |
| 호환 인증 | fixture별 oracle·불변식·서버 도달 횟수·증거 파일을 지정하고 skip을 통과로 간주하지 않는다. |

이 수정의 근거는 소스 검토다. 선택할 npm 배포본과 commit은 P0에서 고정해야 하며 main/master 소스 자체가 지원 버전 인증은 아니다. [S03–S09, S13–S16]

## 2. 설치·사용 경험

### 2.1 기본 npm recipe

**제안 설정 / 예상 결과:** 실제 패키지가 출시된 뒤 같은 이름의 직접·전이 import가 replacement를 사용한다. 지금 설치 가능한 패키지라는 뜻이 아니다.

```json
{
  "dependencies": {
    "@google-cloud/datastore": "10.1.0",
    "@grpc/grpc-js": "npm:workers-grpc-adapter@0.3.0"
  },
  "overrides": {
    "@grpc/grpc-js": "$@grpc/grpc-js"
  }
}
```

설정은 npm workspace의 **실제 루트**에 둔다. 직접 alias만으로는 다른 버전 범위를 요구하는 nested dependency까지 교체했다고 보장하지 않는다. 설치 검사는 GAX 각각의 위치에서 resolve한 경로를 기록한다. npm의 root overrides와 `$` 참조 문법을 사용한다. [S01]

패키지 매니저별 recipe를 자동 추측하지 않는다. 최초 필수는 고정한 npm 버전의 `npm install`·`npm ci`다. pnpm/Yarn은 별도 호환 인증 후 추가한다. native Node 서버도 같은 monorepo에 있으면 workspace를 분리하거나 Worker 전용 bundler recipe를 검증한다. 루트 override가 다른 배포물까지 바꾸는 사실을 숨기지 않는다.

### 2.2 기본 Workers recipe

**제안 설정 / 예상 결과:** Node 호환 API를 사용할 런타임을 구성한다. 아래 날짜·flags는 검증 후보이며 gRPC 변환 beta를 활성화하는 설정이 아니다.

```json
{
  "name": "datastore-drop-in-example",
  "main": "src/index.ts",
  "compatibility_date": "2026-09-21",
  "compatibility_flags": ["nodejs_compat"]
}
```

Cloudflare 발표는 outbound gRPC-Web 변환과 private beta를 설명한다. 계정의 실제 사용 가능 여부는 배포 E2E로 확인하며 존재를 확인하지 않은 beta flag를 발명하지 않는다. 서버가 이미 gRPC-Web을 제공하면 변환 기능 없이도 해당 경로를 시험할 수 있다. [S02]

**제안 코드 / 미실행, 예상 결과:** 기존 Datastore import와 get 호출이 gRPC-Web 경로를 사용한다.

```ts
import { Datastore } from '@google-cloud/datastore';

interface Env {
  GCP_PROJECT_ID: string;
  GCP_CLIENT_EMAIL: string;
  GCP_PRIVATE_KEY: string;
}

export default {
  async fetch(_request: Request, env: Env): Promise<Response> {
    const datastore = new Datastore({
      projectId: env.GCP_PROJECT_ID,
      credentials: {
        client_email: env.GCP_CLIENT_EMAIL,
        private_key: env.GCP_PRIVATE_KEY,
      },
    });
    const [entity] = await datastore.get(datastore.key(['AdapterSmoke', 'fixture']));
    return Response.json({ found: entity !== undefined });
  },
};
```

존재 여부는 미리 준비한 fixture와 비교한다. 없는 entity의 get을 무조건 NOT_FOUND 오류라고 가정하지 않는다. Datastore에 없는 cleanup 메서드를 만들어 예제에 넣지 않는다. SDK 전체 close API가 없는 경우 transaction·SDK stream의 실제 종료 API와 내부 transport의 소유권으로 정리한다.

### 2.3 gateway 설정

**제안 코드 / 미실행, 예상 결과:** 정확히 허용한 논리적 authority만 신뢰 gateway로 전송한다.

```ts
import { configureWorkersGrpc } from '@grpc/grpc-js/config';

configureWorkersGrpc({
  mode: 'grpc-web',
  endpoints: {
    'datastore.googleapis.com:443': 'https://datastore-gateway.example',
  },
});
```

gateway가 보는 bearer token과 protobuf payload는 신뢰 경계다. 공개 샘플 gateway나 임의 query parameter의 upstream URL로 보내지 않는다. gateway는 원래 native service의 authority를 올바르게 설정해야 한다. 논리적 token audience를 gateway 주소로 바꾸지 않는다.

## 3. 제품 범위·런타임 범위

| 항목 | 최초 인증 대상 | 처리 |
|---|---|---|
| Datastore data API | 필수 | CRUD, query, aggregation, transaction, SDK stream |
| Secret Manager | 회귀 | getSecret, accessSecretVersion, listSecrets |
| 직접 grpc-js client | 필수 | Unary·server streaming·metadata·interceptors |
| Client streaming/bidi | 비지원 | 기존 call 표면 반환 후 비동기 UNIMPLEMENTED |
| grpc.Server / native HTTP2 | 비지원 | 사용 시 명시적 비지원 오류 |
| mTLS/custom CA/certificate pinning | 비지원 | credentials/config 단계에서 거부 |
| gzip 등 메시지 압축 | 비지원 | 요청 옵션은 구성 오류, 응답 압축은 UNIMPLEMENTED |
| grpc-js 연결 풀·resolver·LB·retry | 비지원 | 활성화 옵션 거부, SDK의 상위 retry는 유지 |
| waitForReady/channelz | 비지원 | 가짜 READY·가짜 원격 health를 제공하지 않음 |
| Google 모든 API/Admin/LRO | 비인증 | 선택 SDK의 import/초기화에 필요한 표면만 수용, 기능 인증과 분리 |
| 순수 browser | 비대상 | 서비스 계정 secret과 Node SDK를 브라우저에 배치하지 않음 |
| Cloudflare Workers | 첫 필수 | 실제 workerd 및 배포 계정 시험 |
| Node + grpc-web endpoint | 기준 환경 | 상호운용과 패키징 시험 |
| Bun/Deno 및 기타 Edge | 후보 | 동일 전체 SDK suite 통과 후에만 표에 추가 |

Datastore의 data service RPC는 확인한 proto에서 unary다. `runQueryStream()`·`createReadStream()`은 SDK가 만든 object stream이며 RPC 형태 자체의 server/bidi streaming과 구분한다. 따라서 두 종류의 stream 시험이 모두 필요하다. [S14–S17]

## 4. 모듈 구조·소스 재사용·패치 경계

```text
app business module (변경 없음)
  → Datastore → GAX
  → @grpc/grpc-js (alias)
  → vendored Client / factory / interceptors / Metadata / credentials
  → WorkersChannel.createCallForMethod(final method + call options)
  → WorkersCall + byte transport + binary grpc-web decoder
  → fetch → Cloudflare 변환 또는 명시적 gateway → native service
```

### 4.1 모듈별 책임

| 파일/디렉터리 | 책임 | 하지 않는 것 |
|---|---|---|
| `src/facade/index.ts` | 검증된 root exports | 원본 grpc-js 런타임 import |
| `vendor/client/*` | callback/stream/interceptor/serialization/public type 유지 | HTTP2 channel, resolver, server 복사 |
| `src/config.ts` | 한 번 구성, immutable snapshot | 토큰 캐시·요청 상태·자동 환경 탐지 |
| `src/channel.ts` | target/options/credentials/active call 소유 | 네트워크 연결 풀·원격 health 추측 |
| `src/call.ts` | 준비/요청/읽기/종료 상태기계 | protobuf 스키마 해석·재시도 |
| `src/credentials.ts` | HTTPS credentials 및 composition | OAuth 재구현 |
| `src/transport.ts` | URL/header/fetch/AbortController | HTTP2 구현 |
| `src/wire/*` | incremental frame·trailer·binary metadata | SDK 객체 변환 |
| `src/options.ts` | 이름별 허용/거부/무시 정책 | 임의 unknown 옵션 무시 |
| `src/build/*` | 지정 Datastore 프로파일의 정적 asset/codec 변환 | 범용 Node/polyfill 시스템 |
| `src/doctor/*` | 설치 해석·번들·manifest 검증 | 실제 Google 요청·비밀 조회 |

### 4.2 최소 패치 목록

| 패치 ID | 위치 | 변경 | 반드시 보존할 것 |
|---|---|---|---|
| P-01 | Client의 기본 channel 생성 | WorkersChannel 선택 | 주소/credentials/options 검사, 기존 Client 메서드 |
| P-02 | interceptor 하단 bridge | final MethodDefinition과 최종 CallOptions를 자체 Channel에 전달 | user transformer, 인터셉터 실행 순서·serialize/error 처리 |
| P-03 | make/load client factory | 같은 vendored Client를 참조 | `.service`, `.serviceName`, originalName 별칭, 정의 metadata |
| P-04 | credentials factories | 기본 HTTPS credentials로 변경 | CallCredentials 생성·결합 API |
| P-05 | root exports·import closure | client-only graph·명시적 unsupported stubs | 확인한 public 타입과 필요한 deep path |
| P-06 | 타입-only 의존 경계 | runtime http2 import가 남지 않게 정리 | Incoming headers 등에 필요한 구조 타입 |

원본 export `Client`만 바꾸면 factory의 내부 Client 참조가 바뀌지 않는다. 또한 Channel.createCall의 기본 인자만으로 RPC 종류를 알 수 없다. 이 두 경계를 모두 연결한다. [S03–S06]

**내부 bridge 결정:** alias 모드에서 `callInvocationTransformer`를 임의로 교체하거나 transformer 두 개의 실행 순서를 추측하지 않는다. user transformer와 모든 client/call interceptor가 최종 옵션을 정한 뒤 bottom interceptor에서 자체 Channel에 메서드 정의를 전달한다. 해당 Channel을 private symbol로 식별한다. 외부 ChannelOverride는 drop-in 인증 범위 밖이며 구성 오류로 거부한다. 고급 adapter 모드의 같은 메서드 정보 전달은 공유 helper를 사용하되, 원본 임의 버전 Channel과 혼합 호환을 약속하지 않는다.

`CallOptions.deadline === undefined` 여부도 이 bridge에서 보존한다. 원본의 내부 기본화 이후에는 생략과 Infinity가 구분되지 않을 수 있으므로 미리 provenance를 기록한다. `setCredentials()`는 fetch 시작 전 최종 call credentials로 연결한다.

### 4.3 upstream 관리

`vendor/UPSTREAM.json`에 npm version·tarball integrity·commit·원본 파일별 SHA-256·patch 목록을 저장한다. 실제 pin 전 값은 `null`이며 인증 실패 조건이다. 원본 LICENSE/NOTICE를 포함하고 변경 파일을 식별한다. 완성된 거대 bundle을 수정 이력 없이 vendor하지 않는다.

replacement runtime은 원본 `@grpc/grpc-js`를 dependency/peer로 요구하지 않는다. 이름이 자기 자신을 가리키는 alias 재귀도, 별도 upstream alias로 전체 HTTP2 stack을 불러오는 우회도 쓰지 않는다. 원본은 별도 baseline 소비자 fixture에만 설치한다. production import graph의 type-only 참조와 실행 가능한 transport 참조를 구분하여 검사한다.

## 5. 공개 API: grpc-js 호환 root

### 5.1 API 표면의 등급

| 등급 | 의미 |
|---|---|
| S — 지원 계약 | 런타임·타입·관찰 가능한 의미를 호환성 시험으로 확인해야 한다. |
| I — import-only | 선택한 SDK 초기화에 필요한 이름은 존재하나 사용 시 명시적 실패한다. |
| T — type-only | 선언에 필요하나 런타임 기능 제공 주장이 아니다. |
| U — 미지원 | export/path가 없거나 문서화한 오류로 실패한다. |

`exports-contract.json`은 실제 pin한 upstream과 소비자 import 목록을 근거로 자동 생성 후 검토한다. "grpc-js의 모든 exports 지원" 같은 포괄 문구는 쓰지 않는다.

| root API | 등급 | 구체 계약 |
|---|---|---|
| `Client` | S | ctor, close, getChannel, unary/server-stream request 메서드 |
| `Channel` | S/제한 | 논리적 target/active Call 관리. native 연결 상태 기능은 제한 |
| `Metadata` | S | constructor/set/add/remove/get/getMap/clone/merge 및 검증한 옵션 |
| `ChannelCredentials`, `CallCredentials`, `credentials` | S/제한 | 7장의 HTTPS·metadata composition 계약 |
| `status`, `connectivityState` | S | 고정 upstream의 숫자 값과 이름 유지 |
| `loadPackageDefinition` | S | 서비스/메시지/enum definition과 factory metadata 유지 |
| `makeGenericClientConstructor` 및 검증한 별칭 | S | 생성 메서드와 callback overload, 원래 이름 별칭 유지 |
| `InterceptingCall`, `Interceptor`, builder 계열 | S | 선택 client interceptor API. 예외·cancel·deadline 변경 시험 |
| `ClientUnaryCall`, `ClientReadableStream` 관련 표면 | S | cancel/getPeer/metadata/status/error/data/end의 기준 계약 |
| `ClientWritableStream`, `ClientDuplexStream` | I/T | 생성 시 표면은 반환되나 비지원 RPC의 오류를 비동기 전달 |
| `closeClient`, `getClientChannel` | S | 원본 helper 의미, 같은 Channel identity |
| `waitForClientReady`, `Client.waitForReady` | 제한 | callback에 비지원 오류, 네트워크 0회, 성공 callback 금지 |
| `Server`, 서버 credentials/서비스 API | I/T 또는 U | 필요 import만 stub. instantiate/bind/start는 명시적 실패 |
| resolver/LB/channelz 관리 export | U | 원격/native 동작 흉내 금지 |

### 5.2 메서드 signature 보존 정책

공개 grpc-js signatures 전체를 문서에서 임의로 재작성하지 않는다. pin한 upstream의 client `.d.ts`를 재사용하고 AST/API snapshot diff로 보존한다. 타입 테스트는 다음 overload 형태를 실제 generated client와 `Client.makeUnaryRequest` 모두에서 확인한다.

```text
unary(request, callback)
unary(request, metadata, callback)
unary(request, options, callback)
unary(request, metadata, options, callback)
serverStream(request)
serverStream(request, metadata)
serverStream(request, options)
serverStream(request, metadata, options)
```

위는 **API 형태 명세이며 실행 결과가 아니다**. generated service별 구체 요청/응답 타입, callback nullable error, options의 정확한 optional 여부는 pin된 선언이 기준이다. 반환 타입을 모두 Promise로 바꾸거나 Buffer를 무조건 Uint8Array로 바꾸지 않는다. `new Client()`/`extends Client`/factory 생성 경로가 동일 transport를 선택해야 한다.

### 5.3 동기 오류와 비동기 오류

| 발생 지점 | 오류 전달 |
|---|---|
| 잘못된 target·TLS 구성·알 수 없는 Channel 옵션 | 생성자 또는 구성 함수가 동기 configuration error를 throw |
| 호출 인자 overload가 원본 규칙을 어김 | vendored Client의 원래 동기 검증 유지 |
| API는 유효하나 bidi/client stream 비지원 | 반환한 call 표면에 비동기 terminal error/status. callback/listener 설치 기회 제공 |
| credentials generator 실패 | RPC 상태로 비동기 전달; 익명 재시도 금지 |
| 직렬화/역직렬화 실패 | vendored interceptor의 원래 gRPC error 의미 유지 |
| 네트워크·trailer·deadline 실패 | 하위 status로 전달하여 원본 Client가 ServiceError 생성 |
| 사용자 callback 자체의 throw | transport 오류로 바꾸지 않음. 정리는 먼저 완료하고 원래 예외 모델 유지 |

### 5.4 이벤트 계약

필수 비교 대상은 **각 표면**이다: unary callback `(error, value)`, call의 `metadata`, `status`, readable stream의 `data/error/end/close` 및 custom SDK `info` 이벤트. "최종 코드 하나"만 비교하지 않는다.

예를 들어 검토한 원본 Client는 unary의 메시지 수가 잘못되었을 때 callback용 오류를 만들지만 원래 status 객체를 별도 이벤트로 방출할 수 있다. 이를 adapter가 보기 좋게 통일하면 drop-in이 아니다. 정확한 event trace는 pin한 native 실행으로 생성하고 transport-independent 순서와 payload만 비교한다. [S03]

## 6. 공개 API: 설정·엔트리포인트·패키징

### 6.1 설정 타입

아래는 동봉 `contracts/config.d.ts`의 핵심 발췌다. **제안 타입이며 런타임 미구현. 예상 결과:** 잘못된 mode 조합은 typecheck에서, 숫자 범위·URL·수명주기는 runtime validator에서 거부된다.

```ts
type WorkersGrpcConfig = {
  defaultTimeoutMs?: number;
  transportMaxSendBytes?: number;
  transportMaxReceiveBytes?: number;
} & (
  | { mode?: 'cloudflare'; endpoints?: never; allowInsecureLocalhost?: never }
  | {
      mode: 'grpc-web';
      endpoints: Readonly<Record<string, string>>;
      allowInsecureLocalhost?: boolean;
    }
);

configureWorkersGrpc(config: WorkersGrpcConfig): WorkersGrpcConfigSnapshot;
getWorkersGrpcConfig(): WorkersGrpcConfigSnapshot;
```

### 6.2 필드 계약

| 필드 | 기본값 | validation·적용 |
|---|---:|---|
| mode | `cloudflare` | `cloudflare` 또는 `grpc-web`만 허용 |
| defaultTimeoutMs | 없음 | 양의 finite safe integer. 0/음수/NaN/Infinity 거부. call의 명시적 deadline이 항상 우선 |
| transportMaxSendBytes | 33,554,432 | 양의 safe integer, 최대 2^31−1. SDK/channel 제한과 min |
| transportMaxReceiveBytes | 33,554,432 | 동일. stream 전체가 아닌 개별 메시지 payload 상한 |
| endpoints | 비어 있음 | grpc-web mode에서만 필수. 빈 mapping은 거부. 정규화 authority별 하나의 origin |
| allowInsecureLocalhost | false | grpc-web의 로컬 시험 전용. literal loopback과 무인증만 허용 |

고정 정책: 요청 metadata·응답 headers·trailer 각각 65,536 bytes; 12.3장의 계산식 적용. 상한 숫자는 라이브러리 안전 정책이지 Cloudflare/Datastore의 공식 한도가 아니다. 최대 설정값까지 runtime 메모리가 충분하다는 뜻도 아니다.

### 6.3 설정 수명주기

상태는 `unconfigured → configured → locked`다. 기본 설정으로 Channel이 생성되면 `unconfigured → locked`도 가능하다.

첫 `configure`는 순수 validation 후 deep clone/freeze한다. 값이 정규화 기준으로 동일한 재호출은 idempotent 성공이다. Channel 전이라도 다른 값의 두 번째 configure는 `WGA_CONFIG_ALREADY_SET`, 첫 Channel 이후 변경은 `WGA_CONFIG_LOCKED`다. 검사 실패는 이전 상태를 바꾸지 않는다. `getWorkersGrpcConfig()`는 read-only snapshot을 반환하며 network·lock을 유발하지 않는다.

모듈 전역에는 설정만 둔다. credential/token/current request/current method/reader/AbortController를 넣지 않는다. 테스트의 reset은 public export가 아닌 분리된 내부 fixture 도구다. 앱이 런타임마다 설정을 바꾸어 병렬 요청을 경합시키는 API는 제공하지 않는다.

### 6.4 error 타입·진단 식별자

구성 오류는 `WorkersGrpcConfigurationError extends Error`이며 안정적인 `code`를 갖는다. `name/message`만 파싱하는 테스트를 권장하지 않는다. 대표 code: `WGA_INVALID_CONFIG`, `WGA_CONFIG_LOCKED`, `WGA_INVALID_TARGET`, `WGA_UNMAPPED_TARGET`, `WGA_UNSUPPORTED_OPTION`, `WGA_UNSUPPORTED_TLS`.

RPC 실패는 root의 기존 `ServiceError`를 유지한다. adapter 진단 ID는 민감하지 않은 `details` prefix에 넣되 remote metadata에 신뢰용 마커를 추가하지 않는다. RPC 코드와 진단 코드는 별개다. 사용자에게 원본 secret·token·routing resource name을 포함한 임의 cause string을 자동 노출하지 않는다.

### 6.5 엔트리포인트 계약

| 설치 이름 기준 경로 | 실행/타입 | 계약 |
|---|---|---|
| `@grpc/grpc-js` | ESM/CJS/types | client facade |
| `@grpc/grpc-js/package.json` | JSON | 실제 replacement 이름·버전. upstream 버전 가장 금지 |
| `@grpc/grpc-js/build/src/client` | ESM/CJS/types | 확인한 GAX import/type 호환. root와 같은 Client |
| `@grpc/grpc-js/config` | ESM/CJS/types | 위 선택 구성 API |
| `@grpc/grpc-js/adapter` | ESM/CJS/types | 고급 수동 주입, 기본 quickstart 아님 |
| `@grpc/grpc-js/build` | Node build/types | 15장의 제한된 빌드·doctor API |

확인한 GAX는 root 외에 package.json과 client 타입 경로도 참조한다. 실제 JS와 d.ts import inventory를 추출하여 필요한 추가 경로만 등록한다. wildcard로 upstream 내부 전체를 노출하지 않는다. [S13]

canonical CJS 구현 하나에 ESM wrapper가 이름을 연결한다. config와 root/deep path가 같은 module instance를 참조해야 한다. `.mjs/.cjs/.d.ts/.d.cts` 배치와 conditional `exports.types/import/require`를 실제 Node16·NodeNext·bundler 모드로 검증한다. package metadata를 읽는 GAX의 사용자 에이전트에는 replacement 실제 버전이 나타날 수 있으며 이를 문서화한다.

### 6.6 고급 adapter API

`createWorkersGrpcTransport(config?)`는 선택적 instance 설정을 갖는 factory로 유지한다. 반환값은 `channelCredentials`, `grpcOptions(existing?)`, `gaxOptions(existing)`이며 같은 내부 facade/Channel/Call을 사용한다. `grpcOptions`는 `ClientOptions`를, `gaxOptions`는 검증한 GAX constructor options의 입력 타입·추가 필드를 보존하여 반환한다. 정확한 overload는 pin 후 선언·실제 SDK 생성자 typecheck로 확정한다.

이 경로에 원본 grpc module·foreign Channel·`sslCreds`·fallback 설정이 이미 있으면 충돌을 검사한다. 자동으로 덮어쓰지 않는다. 다른 grpc-js 버전 객체를 섞는 기능은 제공하지 않는다. instance factory 설정은 global configure/lock을 변경하지 않는다. factory가 만든 branded Channel options로 해당 client에만 적용한다. `gaxOptions` 성공이 alias/drop-in 시험을 대체하지 않는다. 공개 임의 transport plugin registry나 임의 `fetch` 교체 옵션을 만들지 않는다. fake fetch는 internal dependency injection에만 존재한다.

## 7. Credentials·Google 인증 계약

### 7.1 지원 생성 함수

| API | 허용 입력·출력 | 비지원 처리 |
|---|---|---|
| `credentials.createSsl()` / `ChannelCredentials.createSsl()` | 인자 없거나 명시적 null/undefined 기본 TLS → HTTPS credentials | CA/key/cert/verification option이 실질적으로 지정되면 WGA_UNSUPPORTED_TLS |
| `credentials.createInsecure()` | 로컬 시험에서만 사용하는 logical insecure credentials | production Channel에 연결하면 구성 오류 |
| `credentials.createFromMetadataGenerator(fn)` | 고정 upstream의 callback generator와 Metadata 사용 | callback 여러 번이면 첫 완료만 유효, late rejection/throw 별도 시험 |
| `credentials.createFromGoogleCredential(auth)` | GAX가 공급하는 기존 인증 객체 adapter | 임의 cloud auth API를 새로 구현하지 않음 |
| `credentials.combineChannelCredentials(channel, ...calls)` | 원래 객체 불변, 새 결합 객체 | 다른 구현/알 수 없는 channel credential 거부 |
| `credentials.combineCallCredentials(...calls)` | 원본 compose 순서·오류 의미 | 실패 후 익명 호출 금지 |
| `CallCredentials.generateMetadata(options)` | service_url·method_name을 원래 logical service 기준으로 생성 | gateway 주소를 audience로 사용하지 않음 |
| call의 `setCredentials()` | 최종 per-call creds를 start 이후 준비 단계에도 연결 | fetch 시작 후 인증 변경 금지 |

Google SDK는 alias된 기본 grpc module에서 SSL credentials와 Google CallCredentials를 만든다. 따라서 사용자가 SDK마다 auth interceptor를 추가할 필요가 없다. Google auth의 OAuth/JWT·갱신·scopes·quota project 처리와 SDK retry는 상위 라이브러리 책임으로 유지한다. [S08, S13]

### 7.2 metadata 생성 순서

`start`에서 caller metadata를 clone한다. 최종 channel·call credentials를 고정 upstream 순서대로 compose한 후 generateMetadata를 실행한다. compose의 실행 순서, 동시 generator 완료 순서, merge 순서를 구별한다. 순서 보존을 명목으로 병렬 generator를 임의 직렬화하거나 역순으로 합치지 않는다.

논리적 `datastore.googleapis.com:443`와 `/google.datastore.v1.Datastore/Lookup`의 경우 검토한 upstream이 사용하는 service_url/method_name 규칙을 fixture로 고정한다. 특히 `method_name`은 단순 `Lookup`이 아닌 전체 RPC path다. non-default port·IPv6 처리는 pin한 구현과 비교하고 인증되지 않은 target 형태는 거부한다. [S09]

credentials 결과와 caller metadata를 병합한 뒤 authorization 값이 하나인지 검증한다. 중복은 INTERNAL로 실패하고 fetch하지 않는다. 인증 완료 전에 deadline/cancel이 확정되면 이후 metadata는 버리고 fetch 0회를 유지한다. callback이 동기 완료하는 generator와 비동기 Promise 기반 generator 모두 같은 상태기계에서 처리한다.

### 7.3 인증 오류 코드

**v0.2의 일괄 UNAUTHENTICATED 정책을 폐기한다.** 검토한 grpc-js는 generator 오류에 numeric code가 없으면 UNKNOWN을 사용하고 control-plane에 적절하지 않은 status를 INTERNAL로 제한한다. 이것을 고정 upstream helper와 테스트 벡터로 보존한다. [S09, S10]

| generator 오류 | 어댑터 정책 |
|---|---|
| 유효 code 없음 | UNKNOWN |
| UNAUTHENTICATED 등 허용된 오류 code | 그대로 보존 |
| OK/INVALID_ARGUMENT/NOT_FOUND/ALREADY_EXISTS/FAILED_PRECONDITION/ABORTED/OUT_OF_RANGE/DATA_LOSS | 검토한 helper 기준 INTERNAL |
| status 범위를 벗어난 숫자 | INTERNAL + 안전한 WGA_AUTH_METADATA 진단. 명시적 안전 제한 |
| 사용자 취소 또는 deadline이 이미 terminal | 인증 오류 대신 먼저 확정한 terminal 유지 |

원본 플러그인 error message에 비밀이 들어갈 수 있으므로 어댑터가 생성하는 외부 details는 안전한 식별자로 제한한다. **코드는 보존하되 민감한 임의 cause 텍스트는 동일성을 약속하지 않는 의도적 보안 차이**로 기록한다. 로그에도 원문 token·private key·JWT·credential object를 내보내지 않는다.

### 7.4 인증 호환 시험 범위

첫 Google E2E는 명시적 service account credentials다. SDK가 사용한 JWT access 또는 OAuth 토큰 경로를 기록하되 토큰 본문은 기록하지 않는다. fake auth fixture에서는 갱신·동시 요청·만료·오류를 결정적으로 재현한다. 실제 Google E2E의 권한 오류는 전용 최소권한 principal로 확인한다.

파일 기반 ADC, Cloud Run metadata server, external account/WIF, impersonation, user OAuth, custom universe, mTLS 환경변수는 각각 별도 상태로 기록한다. 시험하지 않은 인증 방식을 "Google auth 전체 지원"으로 묶지 않는다. 지원 범위 밖의 환경변수가 mTLS를 요구하면 실패해야 하며 plaintext/TLS 검증 생략으로 우회하면 안 된다.

## 8. ClientOptions·CallOptions·Metadata 옵션

### 8.1 우선순위

1. SDK/호출자가 명시한 유효 CallOptions.
2. SDK가 생성한 Channel options 또는 고정 grpc-js의 해당 기본값.
3. 패키지의 선택적 deadline 기본값과 transport safety ceiling.

이는 모든 필드에 단순 object spread를 하라는 뜻이 아니다. deadline은 명시값 우선, message limit은 유한한 상한들의 최솟값, credentials는 composition, headers는 소유권·중복 검사를 따른다.

### 8.2 Channel 옵션 표

| 옵션 | 수용 조건·의미 |
|---|---|
| `grpc.max_send_message_length`, `grpc.max_receive_message_length` | 정수 `-1` 또는 0 이상. -1은 grpc 계층 무제한, safety ceiling은 유지. 0은 빈 메시지만 허용 |
| `grpc.default_compression_algorithm` | identity 값만 허용. 나머지 reject |
| `grpc.primary_user_agent`, `grpc.secondary_user_agent` | 정규화·길이 검사 후 x-user-agent 정책에 반영; authorization 등으로 전용 금지 |
| `grpc.default_authority`, `grpc.ssl_target_name_override` | 정규화 logical authority와 동일할 때만 수용. 가짜 TLS 검증 대상 변경 금지 |
| `grpc.enable_retries` | 0만 수용. 1은 비지원; 누락은 adapter retry 없음 |
| `grpc.enable_channelz` | 0만 수용. 가짜 등록/metric을 만들지 않음 |
| `grpc.initial_reconnect_backoff_ms` | 선택 GAX가 넣는 기본 1000만 문서화된 무시 후보. 정확한 값·버전은 fixture로 고정 |
| `grpc.max_reconnect_backoff_ms`, keepalive 계열 | 명시하면 거부. fetch에 해당 동작이 없음 |
| `grpc.service_config`, resolver/LB/proxy/session/connection age/flow-control 옵션 | 명시하면 거부. 일부 JSON을 읽고 나머지를 조용히 무시하지 않음 |
| `interceptors`, `interceptor_providers`, `callInvocationTransformer` | 선택 client API를 그대로 사용. 원본의 상호 배타·조합 검증 보존 |
| `channelOverride`, `channelFactoryOverride` | alias 기본에서는 foreign implementation 거부. 고급 factory가 만든 자체 branded 값만 지원 |
| 알 수 없는 키 | constructor configuration error. `options-policy.json`에 등록 없이 무시 금지 |

GAX가 실제 전달하는 기본 `-1` 길이 제한과 reconnect option은 소스 검토로 확인되지만, 버전이 바뀌면 설치·bootstrap 시험이 다시 필요하다. [S13]

### 8.2.1 effective message limit의 계산 예

검토한 upstream 기본값은 송신 -1(제한 없음), 수신 4MiB다. 선택 GAX가 두 값을 -1로 명시하는 경우에는 그 명시값이 기본값보다 우선한다. [S27]

```text
grpcLimit = 명시 channel 값이 있으면 그 값, 없으면 pin한 upstream 기본값
effectiveLimit = grpcLimit == -1 ? safetyCeiling : min(grpcLimit, safetyCeiling)
```

**정책상 예상 결과:** standalone client의 기본 수신은 4MiB, GAX가 -1을 전달한 호출은 기본 safety ceiling인 32MiB다. 명시한 1MiB는 1MiB, 명시한 0은 빈 payload만 허용한다. response 전체 길이나 protobuf 역직렬화 후 객체 크기의 상한이 아니다. 4MiB를 넘되 32MiB 이내인 통제된 응답을 GAX fixture에서 검사해 숨은 4MiB 제한이 남지 않았는지 확인한다. 실제 Google 엔티티/쿼리의 제품 한도를 이 테스트로 확대한다고 설명하지 않는다.

### 8.3 호출·metadata 옵션

| 옵션 | 정책 |
|---|---|
| CallOptions.deadline | Date 또는 number의 원본 형식. finite/Infinity/미지정 구분. 11장 참조 |
| CallOptions.credentials | 기존 CallCredentials를 합성. fetch 뒤 변경 불가 |
| CallOptions.host | 정규화 logical authority와 같을 때만 허용 |
| CallOptions.parent / propagate_flags | 실제 parent propagation 요구는 비지원. 기본/없음만 수용 |
| CallOptions.interceptors / providers | 기존 조합 계약. 요청 인자·metadata·deadline을 바꾼 결과를 transport가 받음 |
| Metadata.idempotentRequest / cacheableRequest | hint는 보존하나 adapter retry/cache/GET으로 확대 해석하지 않음 |
| Metadata.waitForReady=true | 비지원 RPC 오류, no ready loop; false/기본은 허용 |
| Metadata.corked=true | 최초 버전 비지원으로 명확히 실패. false/기본은 허용 |
| message write flags | 기본 및 의미가 보존되는 identity 전송만 허용. 압축을 요구하는 flags는 거부 |

구성 오류가 비즈니스 호출 반환 surface를 바꾸지 않도록, Channel 생성 시 알 수 있는 것은 생성자에서, 호출에서만 알 수 있는 것은 Call의 비동기 terminal로 전달한다. 지원 flags의 정확한 상수값은 pin한 public enum을 사용한다.

## 9. Channel 내부 계약

### 9.1 소유하는 상태

`logicalTarget`, `normalizedAuthority`, `route`, `credentials`, `validatedOptions`, `readonlyConfig`, `closed`, `activeCalls:Set`, `nextCallId`만 보관한다. 생성자는 네트워크를 열지 않으며 activeCalls는 요청을 시작한 call의 수명만 추적한다. random 글로벌 call index에 인증정보를 넣지 않는다.

| 메서드 | 계약 |
|---|---|
| `getTarget()` | 사용자가 준 target의 지원된 원래 표현. 실제 gateway URL과 구별 |
| private `createCallForMethod(context)` | final method/serialization shape/options/deadline provenance를 검증하고 새 WorkersCall 생성 |
| public/internal `createCall(...)` 직접 호출 | RPC-kind context가 없으면 명시적 비지원. 임의 unary로 추측하지 않음 |
| `close()` | idempotent. closed를 먼저 표시, 활성 Call을 UNAVAILABLE로 종료, 신규 Call 금지 |
| `getConnectivityState()` | 열림 IDLE, 닫힘 SHUTDOWN. READY나 실제 연결을 추측하지 않음 |
| `watchConnectivityState()` | code=UNIMPLEMENTED인 Error를 비동기 callback. timer/health fetch 없음 |
| `getChannelzRef()` | 타입 계약에 필요한 비등록 local 식별자. channelz 서비스를 제공하지 않음 |
| Call의 `getPeer()` | 문서화된 logical endpoint 문자열; 실제 remote IP 아님 |
| Call의 `getAuthContext()` | null. 검증하지 않은 peer certificate context를 생성하지 않음 |

getPeer/연결 상태/channelz는 native transport와 같지 않은 의도적 제한이다. support report에서 제외/차이를 명시하고 테스트로 확인한다.

### 9.2 호출 context

**설계 모델 / 미구현, 예상 결과:** 아래 의미의 immutable context가 매 Call에 전달된다. 공개 API가 아니다.

```text
CallContext {
  callId, logicalAuthority, methodPath,
  requestStream, responseStream,
  finalCallOptions, deadlineWasSpecified,
  channelCredentials, messageLimits,
  routeOrigin, startTimestamp
}
```

serialize/deserialize는 원본 interceptor가 담당한다. transport는 schema를 받거나 response object를 조립하지 않는다. 동일 method를 병렬 호출해도 context가 공유되지 않는다. path만 key로 한 임시 map이나 `currentMethod` 전역 변수는 금지한다.

## 10. Call 상태기계·불변식·정리

### 10.1 상태와 준비 플래그

```text
CREATED → PREPARING → FETCHING → READING → TERMINAL
    └────────── cancel / deadline / error ──────────┘
```

별도 플래그는 `listenerInstalled`, `authReady`, `requestReceived`, `halfClosed`, `readDemand`, `pendingMessage`, `trailerCandidate`, `readerDone`, `finishScheduled`, `writeAcked`다. 하나의 enum으로 병렬 auth와 request 준비를 표현하려고 복잡한 중간 상태를 늘리지 않는다.

| 입력 | 사전 조건 | 동작·다음 상태 |
|---|---|---|
| `start(metadata, listener)` | start 1회 | metadata clone, auth 시작, 기존 terminal이 있으면 비동기 통지 |
| `sendMessageWithContext(ctx, bytes)` | 지원 RPC, request 미수신 | 길이 검사, 독립 소유 bytes 확보, write completion 예약 |
| 두 번째 request message | unary/server streaming | INTERNAL 또는 고정 client 오류 경로. fetch 전이면 network 0회 |
| `halfClose()` | closed 아님 | halfClosed 표시, 준비 predicate 검사 |
| auth 성공 | terminal 아님 | metadata 검증, authReady, predicate 검사 |
| 준비 predicate 참 | listener/auth/request/halfclose/유효 deadline | fetch **한 번** 시작 |
| response headers | FETCHING | content/status 검증, initial metadata 전달, READING |
| `startRead()` | terminal 아님 | readDemand=true, pump 재개. 여러 호출은 demand boolean을 불필요하게 누적하지 않음 |
| frame message | demand 있음 | pending 제거 후 listener에 메시지, reentrancy-safe 상태 갱신 |
| trailer + EOF | protocol intact | finish(candidate status) |
| cancel/deadline/error | 아직 terminal 아님 | finish 지정 사유 |

빈 protobuf 메시지는 0바이트 request가 **존재하는 것**이지 미전송이 아니다. `halfClose()`만 있고 request가 없으면 fetch하지 않는다. 지원하지 않는 RPC는 auth 전에 실패 전용 Call로 생성한다.

### 10.2 핵심 불변식

I-01: 데이터 RPC fetchCount ≤ 1. auth HTTP 요청은 별도 카운터다.  
I-02: final status delivery ≤ 1; listener가 있는 유효 call은 최종적으로 정확히 1회.  
I-03: write callback이 공급되었으면 완료 ≤ 1 및 종료 시 미완료 없음.  
I-04: terminal 이후 새 metadata/message 전달·fetch 시작 없음.  
I-05: callback/listener 호출 전에 상태를 갱신하여 재진입 안전성 확보.  
I-06: 종료 후 activeCalls·timer·adapter-owned request/response buffer 참조 없음.  
I-07: call A cancel은 call B의 auth/reader/status에 영향을 주지 않음.  
I-08: reader pump는 동시에 최대 1개. readDemand가 false이면 새 메시지를 연속 방출하지 않음.

### 10.3 `finish(status, origin)`의 순서

1. terminal이면 return한다. 아니면 terminal로 바꾸고 immutable status를 저장한다.
2. deadline timer와 대기 작업을 해제하고 Channel activeCalls에서 제거한다.
3. 정상 EOF가 아니면 AbortController를 abort하고 reader.cancel을 요청한다. cancel 자체의 rejection은 처리한다.
4. 보유 request·pending frame·metadata 임시 참조를 해제한다. 정상 terminal에서 전달할 최종 metadata는 별도 보존한다.
5. 미완료 write callback을 해당 결과로 한 번 완료한다. 이 callback의 사용자 예외를 network failure로 재해석하지 않는다.
6. listener가 없으면 전달 예약 상태를 저장한다. listener가 있으면 지정된 비동기 전달 경로에서 status를 한 번 전달한다.
7. late auth/fetch/read Promise는 terminal을 확인하여 결과를 폐기하고 rejection을 처리한다. cleanup Promise가 영원히 끝나지 않는다고 terminal 통지를 무기한 지연시키지 않는다.

성공 terminal도 정리를 거쳐야 한다. abort가 이미 완료된 fetch에서 예외를 만들더라도 성공 status를 덮어쓰지 않는다. 메모리·timer 검사에는 public API가 아닌 내부 counter를 사용한다.

### 10.4 write callback의 의미

이 전송의 write completion은 **request bytes가 adapter에 안전하게 수용되었음**을 뜻한다. 서버 반영 또는 network flush 완료를 보장하지 않는다. 원본 Client가 요구하는 callback 횟수·오류 표면을 유지하되 그 transport 의미의 차이를 문서화한다. 입력 Buffer를 복사하지 않고 참조하는 최적화는 caller의 직후 mutation 시험을 통과하기 전까지 사용하지 않는다. 첫 구현은 길이 검사 후 독립 소유 복사를 기본으로 한다.

## 11. Deadline·취소·쓰기 결과 불확실성

### 11.1 deadline 선택 알고리즘

| 최종 호출 설정 | effective deadline |
|---|---|
| finite number / 유효 Date | 해당 절대 deadline |
| `Infinity` | 제한 없음. config default를 적용하지 않음 |
| 생략 | config default가 있으면 call creation time + default, 없으면 제한 없음 |
| NaN / invalid Date / -Infinity | INVALID_ARGUMENT의 호출 오류, auth·fetch 0회 |
| 이미 지난 finite 값 | DEADLINE_EXCEEDED, auth·fetch 0회 |

Date/number는 정확한 upstream 단위인 epoch milliseconds를 사용한다. defaultTimeout은 relative milliseconds다. 매우 먼 deadline은 timer 최대 지연을 넘기지 않게 분할 예약하고 실제 남은 시간을 다시 검사한다. 내부 테스트는 주입 가능한 deterministic clock을 사용한다.

### 11.2 timeout header

fetch 직전 남은 시간을 산출해 gRPC의 최대 8자리와 단위 `H/M/S/m/u/n` 규칙에 맞춘다. wire timeout은 남은 시간을 부당하게 더 짧게 만들지 않도록 반올림 방향을 명시하고, 로컬 절대 deadline은 별도로 지킨다. header encoding 경계값은 golden fixture로 검증한다. 무제한이면 header와 timer를 만들지 않는다. [S19]

SDK의 constructor/initialize/auth client discovery가 Call 이전에 수행한 시간까지 포함한다는 보장은 없다. cold initialization과 Call latency는 별개 측정이다. user handler 전체 timeout은 상위 요청 정책이다.

### 11.3 경쟁·서버 반영

cancel → CANCELLED, deadline → DEADLINE_EXCEEDED, Channel.close → UNAVAILABLE. 정상 trailer를 받았더라도 body EOF 전까지는 status 후보이므로 그 사이 실제 deadline이 먼저 확정되면 deadline을 유지한다. first terminal wins이며 벽시계가 같다는 이유로 임의 성공 우선 정책을 만들지 않는다.

취소는 로컬 응답 소비와 fetch를 중단하는 것이지 이미 실행된 Datastore Commit을 취소하거나 rollback하는 기능이 아니다. 서버가 commit 후 응답을 유실한 경우 실패 status를 반환할 수 있으며 결과는 불확실하다. adapter는 이를 성공/확정 rollback으로 꾸미지 않고 같은 Call을 재전송하지 않는다. 상위 SDK가 새 Call로 재시도하는 경우는 별도로 계측한다.

## 12. Wire 프로토콜·metadata·오류 판정

### 12.1 요청 생성

지원 target은 DNS hostname[:port]와 bracketed IPv6 literal[:port]다. port 생략은 secure 443이다. userinfo/path/query/fragment/임의 resolver scheme은 거부한다. `dns:///...` 같은 native resolver 형식은 첫 버전 비지원으로 명시한다. hostname case와 default port를 정규화하고 endpoint mapping key를 정확히 비교한다. Unicode hostname 지원은 URL 정규화 후 IDNA 표현을 기준으로 별도 fixture를 둔다. 불명확한 authority는 추측하지 않는다.

method는 `/package.Service/Method` 형태를 검증한다. URL 전체·query·`..`·percent-encoded slash로 원래 route를 벗어날 수 없어야 한다. grpc-web mapping value는 origin만 허용하며 서비스 route를 path prefix로 임의 재작성하지 않는다.

```text
POST {selected origin}{method path}
content-type: application/grpc-web+proto
accept: application/grpc-web+proto
x-grpc-web: 1
grpc-accept-encoding: identity
[grpc-timeout: 남은 deadline이 있을 때]
[인증·routing·quota metadata]
body: 0x00 + uint32be(payload.length) + payload
fetch redirect: manual
```

위는 **전송 계약/예상 결과**다. 사용자 metadata의 host/content-length/connection/transfer-encoding/HTTP2 pseudo-header는 허용하지 않는다. content-type·grpc-timeout 등 transport-owned key와 충돌하면 비동기 호출 오류로 실패한다. 몰래 삭제하여 사용자가 보안/프로토콜 옵션이 전달되었다고 오해하게 하지 않는다. [S18, S19]

### 12.2 Incremental frame decoder

decoder 상태는 `HEADER(need 5)`, `PAYLOAD(remaining)`, `TRAILER_PARSED`, `DONE`이다. 현재 chunk의 offset을 보존하고 한번 읽은 bytes를 다시 전체 concatenate하지 않는다. header는 고정 5바이트 작은 버퍼, payload는 검증한 length 이내 allocation 또는 제한된 조각 집합을 사용한다. payload가 완성되기 전 소비자에게 전달하지 않는다.

| 입력 | 결과 |
|---|---|
| flag 0x00 | 비압축 data |
| flag 0x80 | 비압축 trailing metadata |
| flag의 compression bit | 지원하지 않는 encoding이면 UNIMPLEMENTED |
| 예약 bit / trailer 뒤 frame / 중복 trailer | INTERNAL |
| length > effective message limit | allocation 전 RESOURCE_EXHAUSTED |
| trailer length > 65,536 | allocation 전 RESOURCE_EXHAUSTED |
| EOF에서 header 또는 payload 부족 | INTERNAL |
| 정상 frame이지만 최종 status 없음 | UNKNOWN / WGA_STATUS_MISSING |

flags의 예약 bit 검사를 compression 판정보다 먼저 한다. 예약 bit와 압축 bit가 함께 있으면 INTERNAL이다. header의 모든 chunk 분할과 한 chunk의 다중 frame을 지원한다. `0xffffffff` 길이값을 signed 32bit로 읽어 음수나 작은 수로 해석하지 않는다. 길이+5의 산술 overflow를 검사한다. frame body는 protobuf bytes이며 transport 자체가 deserialize하지 않는다.

### 12.3 Metadata 변환

원본 Metadata 객체의 모든 값을 순회한다. `getMap()`은 첫 값만 노출하므로 wire 직렬화에 단독 사용하지 않는다. root Metadata의 validation·clone·merge 의미는 vendored 구현을 유지한다. [S07]

| 항목 | 계약 |
|---|---|
| 일반 metadata | lowercase key, 허용 ASCII 값, 복수 값 보존 가능한 한 append |
| 일반 중복 response header | Fetch가 결합한 경계의 원상 복원까지 약속하지 않음. 의미상 동등한 결합만 허용 |
| `-bin` 송신 | Buffer bytes를 표준 base64로 인코딩 |
| `-bin` 수신 | comma로 결합된 값 분리, whitespace trim, padded/unpadded 검증 후 decode |
| 잘못된 base64 | lenient Buffer.from에 의존하지 않고 protocol error |
| `grpc-status-details-bin` | raw bytes로 보존; Google status protobuf 해석하지 않음 |
| `grpc-message` | UTF-8 percent decode, malformed `%`로 예외 발생 금지, 원문 보존 가능 |
| initial/trailing metadata | 별도 객체. 나중에 caller metadata를 mutate하지 않음 |
| CR/LF/NUL 등 금지 값 | 요청은 호출 오류, 응답은 protocol error |

예산 계산은 직렬화할 각 key/value의 UTF-8 byte 길이 + `: ` 2바이트 + CRLF 2바이트 합계다. binary value는 base64 길이를 사용한다. HTTP2 구현의 wire header compression 크기나 플랫폼 공식 header 한도를 측정하는 규칙이 아니다. 요청 headers, 노출된 response headers, trailer payload에 각 64KiB를 별도로 적용한다. body trailer는 CRLF 기반 header block을 검증하고 임의 obs-fold를 지원하지 않는다. [S19]

### 12.4 response/status 우선순위

1. **3xx:** redirect를 따르지 않고 body를 정리한다. WGA_REDIRECT_BLOCKED + 공식 HTTP fallback status를 사용한다. authorization 재전송 0회.
2. **명백한 protocol integrity 위반:** 손상 framing·충돌 status·trailer 이후 데이터 등은 INTERNAL. 유효한 숫자 status가 어딘가 있었다는 이유로 무시하지 않는다.
3. **유효한 grpc-status:** 0–16의 엄격한 숫자 표기와 정확히 한 final status를 검증하여 사용한다. 중복/모순 값은 protocol error.
4. **status 없음:** 공식 HTTP→gRPC fallback. HTTP200도 UNKNOWN이다.

binary content type은 `application/grpc-web` 및 `application/grpc-web+proto`의 문서화된 파라미터를 수용한다. `application/grpc-web-text`·예상치 않은 JSON/HTML은 decoder에 무작정 넣지 않는다. status가 없는 비-grpc body는 HTTP fallback과 안전한 진단으로 실패하고 body를 제한적으로 정리한다. body를 로그에 저장하지 않는다.

headers에 grpc-status가 있는 trailers-only 응답은 메시지가 없어야 한다. 유효 non-OK는 그대로 전달한다. 정상 unary의 메시지 개수와 상위 callback 오류는 vendored Client가 판정하게 한다. server stream은 메시지 0개+OK를 허용한다. body trailer status는 EOF까지 후보로 두어 뒤따르는 frame을 검증한다.

| status 없는 HTTP 응답 | gRPC fallback |
|---|---|
| 400 | INTERNAL (13) |
| 401 | UNAUTHENTICATED (16) |
| 403 | PERMISSION_DENIED (7) |
| 404 | UNIMPLEMENTED (12) |
| 429, 502, 503, 504 | UNAVAILABLE (14) |
| 나머지, 200 포함 | UNKNOWN (2) |

이 매핑은 status가 없을 때만 사용한다. [S20]

### 12.5 adapter 오류 표

| 사유 | gRPC code | 진단 ID |
|---|---|---|
| 네트워크 연결 실패 | UNAVAILABLE | 안전한 네트워크 진단 |
| 사용자 취소 / deadline | CANCELLED / DEADLINE_EXCEEDED | 원래 API detail 정책 |
| Channel 종료 | UNAVAILABLE | WGA_CHANNEL_CLOSED |
| 메시지/metadata 상한 | RESOURCE_EXHAUSTED | WGA_MESSAGE_LIMIT / WGA_METADATA_LIMIT |
| 잘린·잘못된 frame | INTERNAL | WGA_PROTOCOL |
| 비지원 bidi/client stream | UNIMPLEMENTED | WGA_UNSUPPORTED_RPC |
| 응답 메시지 압축 | UNIMPLEMENTED | WGA_UNSUPPORTED_COMPRESSION |
| 인증 생성 실패 | 7.3장 기준 | WGA_AUTH_METADATA |
| response status 누락 | HTTP fallback | WGA_STATUS_MISSING |

서버가 만든 non-OK details/metadata는 전송 의미를 보존하되 자동 로그로 출력하지 않는다. adapter 자체 오류의 detail은 안정적·짧은 설명이어야 하고 SDK tuple이나 error subclass를 임의로 새로 만들지 않는다.

## 13. Backpressure·메모리·response 수명

`startRead()`는 소비 수요다. demand가 있으면 pending message 한 개를 전달하고 demand를 지운다. callback이 동기적으로 startRead를 다시 호출해도 중복 pump가 실행되지 않게 scheduler flag로 합친다. demand가 없으면 다음 message 방출을 중단한다.

종료 trailer를 발견하려면 제한된 look-ahead가 필요하다. **완성된 pending message 최대 1개 + 조립 중 message 최대 1개**까지만 adapter가 보유한다. pending이 가득 차면 reader.read를 추가 실행하지 않는다. 전달 직후에는 그 참조를 먼저 지우고 listener를 부른다. unary는 한 번의 startRead만으로 정상 trailer를 소비하고 두 번째 message 오류도 발견할 수 있어야 한다.

runtime이 이미 전달한 현재 chunk를 보유하는 비용, Node readable의 highWaterMark, protobuf 객체 크기는 위 adapter 예산과 별개다. 작은 frame이 모인 큰 chunk를 파싱할 때 전체 메시지 객체 배열을 만들지 않는다. stream 총합이 32MiB를 넘어도 개별 메시지가 상한 안이고 소비가 진행되면 처리 가능해야 한다.

클라이언트가 pause한 동안 final status가 뒤에 있으면 그것을 즉시 안다고 보장하지 않는다. resume/cancel/deadline이 진행을 결정한다. response body가 영원히 닫히지 않는 상황에서 명시적 deadline이 없으면 라이브러리가 임의 timeout을 만들지 않는다. 요청 수명 정책은 상위 handler 책임이다.

## 14. 재시도·lifecycle·보안

### 14.1 retry 경계

adapterAttempt=1은 fetch가 한 번 시작되었음을 뜻한다. GAX가 같은 논리적 작업을 새 Call로 다시 호출하면 다른 callId를 가진다. 다음을 각각 기록한다: 비즈니스 작업 수, GAX Call 수, adapter data fetch 수, auth fetch 수, 서버 도달 수. SDK 페이지네이션·Lookup deferred 재조회도 단순 retry와 구분한다.

자동 hedging·HTTP retry·REST fallback·stream replay·Commit 재송신은 없다. 런타임 fetch의 내부 네트워크 동작까지 애플리케이션에서 완전히 계측할 수 있다고 주장하지 않는다. adapter 수준 중복 실행 여부는 통제된 서버의 request IDs와 mutation 기록으로 확인한다.

### 14.2 Workers 요청 수명

기본 예제는 invocation별 SDK instance를 사용한다. immutable schema·설정은 공유할 수 있지만 진행 중 I/O·auth promise·abort signal은 다른 요청에 공유하지 않는다. 모듈 전역 SDK 재사용 패턴은 별도 수명주기/자격증명 격리 시험을 통과하기 전까지 인증하지 않는다. 이는 API import/메서드 무변경 목표와 별개의 bootstrap 제약으로 명시한다.

handler는 필요한 RPC를 await하고 transaction/stream을 완료·중단한다. waitUntil을 무기한 구독 서버로 사용하지 않는다. Node 단위 시험에서만 통과한 timer·crypto·stream·파일 API를 Workers 지원이라고 기록하지 않는다.

### 14.3 보안 검토 항목

SSL 옵션 무시 금지, redirect 차단, 논리적 target allowlist, gateway trust, metadata CRLF, malicious frame length, double-finalization, caller Buffer mutation, 서로 다른 프로젝트/credential의 요청 격리, 문서 예제의 secret 비노출을 필수로 시험한다. production credentials는 loopback insecure mode에서 전송하지 않는다.

관측성 기본값은 무로그다. 선택한 안전한 진단은 method name, 호스트, duration, status, byte count만 포함한다. resource ID·metadata 전체·payload·token·private key·SQL/Query 데이터는 자동 기록하지 않는다. callback/SDK가 출력하는 오류 로그는 adapter 로그와 별도로 점검한다.

## 15. Datastore bootstrap·정적 codec·공식 빌드 프리셋

### 15.1 왜 별도 검증 단계인가

Datastore/GAX는 JSON proto 로딩 외에 common protobuf type과 operations client 초기화도 수행한다. protobufjs는 특정 lazy 경로에서 constructor/codec을 생성할 수 있다. Workers는 eval/new Function을 허용하지 않으므로 "JSON은 파일에 있으니 된다"는 결론을 내리지 않는다. 반대로 filesystem import 하나만 보고 SDK 전체가 불가능하다고 단정하지도 않는다. 실제 런타임이 제공하는 virtual fs와 실제 실행 경로를 확인한다. [S13–S16, S22, S24]

### 15.2 P0 조사·판정 절차

정확한 dependency graph를 고정한 뒤 다음 순서의 실행 trace를 얻는다: 정적 import → SDK constructor → lazy initialize → proto/service definition → 인증 객체 생성 → serializer 첫 실행 → 첫 response deserialize → query/transaction/SDK stream.

각 단계의 동적 require, fs.readFile/loadSync, new Function/eval, codegen 함수, Node crypto/HTTP 호출을 식별한다. AST/source inventory는 runtime 성공 증거의 대체가 아니며 두 증거를 함께 남긴다. 먼저 기본 alias build를 실행한다. 실패가 실제로 codegen/asset 경로 때문이면 공식 프리셋을 제공한다. 실패 원인을 테스트용 global no-op으로 지우지 않는다.

### 15.3 프리셋의 제한된 입력·산출물

**제안 API / 미구현, 예상 결과:** build 단계에서만 고정 profile의 Datastore dependency를 변환하여 Worker entry와 provenance report를 생성한다.

```ts
buildDatastoreWorker({
  projectRoot: '.',
  entry: 'src/index.ts',
  outdir: 'dist/worker',
  profile: 'datastore-candidate-profile',
  sourcemap: true,
});
```

`profile`은 배포 패키지 안에 있는 정확한 인증 ID여야 한다. 위 ID는 후보 예시다. "최신 SDK를 알아서 수정"하는 기능은 없다. 입력 entry는 원본 business module을 참조한다. 출력은 정적 bundle entry, 정적 schema/codec registry, dependency hash, transformed source 목록, build manifest다. 원본 node_modules 파일을 덮어쓰지 않는다.

Wrangler custom build 한 곳 또는 검증한 bundler recipe 하나로 연결한다. `/build`는 Node 전용이며 Worker runtime root에 포함하지 않는다. unsupported version/hash를 발견하면 WGA_UNSUPPORTED_DEPENDENCY 또는 WGA_SCHEMA_MISMATCH로 build를 중단한다.

### 15.4 정적 registry와 변환 계약

키는 **schema content hash + loader options hash + profile revision**이다. 대상은 지정 Datastore service/common google.protobuf types 및 그 SDK가 실제 초기화하는 필요한 dependency closure뿐이다.

정적 산출물은 메시지 constructor, encode/decode, verify, fromObject/toObject, package/service definitions, serializer/deserializer, 필요한 descriptor metadata를 포함한다. keepCase, longs, enums, bytes, defaults, arrays, objects, oneofs와 64비트 정밀도 옵션을 원래 loader 값에 맞춘다. .service metadata와 proto-loader가 요구하는 reflection/fileDescriptorProtos도 실제 소비 경로 기준으로 보존한다.

코드 생성은 **빌드 시 Node**에서만 수행한다. runtime에서는 registry lookup만 하고 unknown schema는 명시적으로 실패한다. byte 단위 schema hash가 달라졌는데 가능한 것처럼 fallback하지 않는다. AST 기준으로 정확한 loader/call site만 교체하며 전역 protobufjs prototype, 임의 애플리케이션의 모든 protobuf load, fs API를 monkeypatch하지 않는다.

특히 protobuf Type의 ctor 설정이 lazy codec 메서드에 영향을 줄 수 있으므로 **constructor를 먼저 고정하고 static encode/decode/fromObject 등 메서드를 나중에 연결**한다. 연결 뒤 encode/decode/fromObject/toObject/reflection을 모두 호출해 codegen 재진입이 없는지 시험한다. Static JSON만 삽입하고 첫 fromObject에서 다시 eval하는 상태는 불합격이다. [S16]

operations client가 import/constructor에서 만들어진다는 이유로 전체 admin/LRO 기능 인증 범위를 확대하지 않는다. 필요한 initialization만 보존하고 admin 호출은 별도 비인증으로 표시한다. lazy unsupported method를 stub으로 바꿀 경우 해당 import-only 계약과 실패 위치를 tests에 기록한다.

### 15.5 빌드 프로파일을 확정하는 조건

P0 전에 정확한 hash/AST 위치를 발명하지 않는다. 프로파일에 null/TBD가 하나라도 있으면 release 인증은 불가능하다. 실제 transformed file의 upstream hash, AST anchor, replacement hash, 필요 schema 목록, loader option snapshot, static-codegen audit, no-preset/preset 결과를 artifact로 남긴다. 사용자에게 파일 복사나 SDK 소스 수정을 맡긴 결과는 drop-in 완료가 아니다.

## 17. 호환성 테스트의 공통 모델

### 17.1 네 종류의 근거를 분리한다

| 구분 | 근거 | 증명하지 못하는 것 |
|---|---|---|
| source_review | 공식 코드·규격을 읽고 호출 경로 확인 | 설치본 실행, 계정 기능 활성화 |
| local_test | Node unit/타입/패키징/로컬 서버 실행 | workerd·배포 Worker 동작 |
| workers_runtime | 실제 workerd 기반 테스트와 bundle 초기화 | 외부 Cloudflare 변환·Google 인증·권한 |
| deployed_e2e | 배포 Worker에서 실제 대상 호출 | 모든 버전/SDK/인증 방식의 일반 호환 |

본 문서 작성에서 수행한 확장 타입·문서 검사는 local_test **중에서도 설계 자산 검사**다. 패키지 런타임을 구현·테스트했다는 의미로 사용하지 않는다. v0.2의 mock alias 실험도 실제 SDK 호환 시험이 아니다.

### 17.2 test case 레코드

동봉 `test-catalog.json`의 필수 필드는 `id`, `requirement_ids`, `title`, `layer`, `fixture`, `procedure`, `expected_result`, `invariants`, `evidence`, `gate`, `execution_status`다. `expected_result`는 **예상 결과**이며 `execution_status=not_run`을 유지한다. actual 결과는 별도 run artifact에만 기록한다.

각 실행 결과에는 git commit, lockfile hash, test code hash, runtime/profile, start/end time, outcome(pass/fail/skipped/blocked), stdout 요약, 서버 trace path, exception code, 필수 invariant 수치를 기록한다. 모든 테스트가 "PASS"라는 자유 텍스트 요약만 있는 보고서는 수용하지 않는다.

### 17.3 기준 구현과 시스템 경계

```text
공유 business.ts ─→ native 소비자 / 원본 grpc-js ───────────→ native fixture server
             └─→ replacement 소비자 / workerd → Envoy ───→ 같은 fixture server

공유 business.ts ─→ native 소비자 ───────────────→ 테스트 Google 프로젝트
             └─→ 배포 Worker / Cloudflare 변환 ─→ 같은 정책의 테스트 Google 프로젝트
```

native fixture server는 원본 grpc-js 서버 또는 독립 구현을 사용하며 replacement를 가져오지 않는다. Envoy의 공식 grpc_web 필터가 local translation을 담당한다. decoder가 만든 예상 값을 그 decoder로 재검증하는 자기검증만으로 끝내지 않는다. 손상 frame은 별도의 raw HTTP responder로 보내고 정상 gRPC interop와 구분한다. [S21]

Workers unit/integration은 공식 `@cloudflare/vitest-plugin` 기반 실행을 후보로 삼고 실제 설치 버전을 pin한다. Node에서 global fetch를 mock한 테스트는 Workers 테스트라고 부르지 않는다. [S23]

## 18. Fixture·oracle·데이터 비교 명세

### 18.1 최소 테스트 service

서비스는 Unary, ServerStream, ClientStream, Bidi 네 형태만 갖는다. 요청 데이터와 서버 동작은 분리한다.

- 일반 request: `case_id`, `payload`, `sequence` 등 작은 명시적 타입.
- 서버 제어: 테스트 프로세스의 별도 control channel/fixture 설정. production metadata 헤더로 임의 실패·sleep을 제어하는 기능은 배포하지 않는다.
- 응답 trace: `case_id`, arrival sequence, method, request byte hash, 안전한 metadata key와 값의 해시, mutate count, send count, abort observed를 기록한다.
- unknown/비지원 method는 고정 status로 반환하고 실제 데이터 RPC와 섞지 않는다.

server streaming은 0/1/다수 메시지, 일정 지연, 중간 non-OK, trailer 직후 끊김, 소비자 pause 상황을 제공한다. client/bidi는 서버에 도달하지 않는다는 것을 fixture counter로 검증한다.

### 18.2 native differential oracle

동일 입력을 두 소비자에 보내 결과를 기록한다. 기준 trace는 테스트 시 pin한 native 패키지로 실제 실행하여 얻는다. 예상 event 순서를 memory나 문서 해석으로만 고정하지 않는다.

| 비교 필드 | 비교 방식 |
|---|---|
| gRPC request path/bytes | byte-identical 또는 독립 decoder로 의미 동등성; 정규화 사유 기록 |
| unary result | SDK 객체 구조·값·타입·undefined/missing 구분 |
| ServiceError | code, details 정책, metadata binary bytes, callback 인자 위치 |
| stream | 메시지 순서·개수, metadata/status/error/end/close의 의미상 순서 |
| auth | 원래 service audience/method, 헤더 존재·생성 횟수; 토큰 원문 저장 금지 |
| retry | business op → GAX Call → fetch → 서버 도달 횟수 |
| cleanup | 활성 call/timer/pump/소유 buffer/미완료 callback 0 |

의도적 차이는 작은 allowlist로 관리한다: peer IP 대신 logical endpoint, transport header, 원격 연결 상태 미지원, 안전한 인증 오류 details, 메시지 safety ceiling, config default timeout이 명시된 경우. 이 allowlist에 임의 값 불일치를 추가하여 실패를 숨기지 않는다.

### 18.3 Datastore 값 비교용 serializer

단순 JSON.stringify로 비교하면 Buffer/Long/Date/undefined/symbol 정보가 사라질 수 있으므로 test-only tagged serializer를 사용한다. 원본 객체를 변환하여 앱에 반환하지는 않는다.

예시 태그: `buffer`+base64, `date`+epoch, `int64`+decimal string+원래 wrapper 여부, `key`+project/database/namespace/path, `undefined`, `missing-property`, `symbol-key`+Datastore.KEY 의미. 객체 필드 키는 비교 안정성을 위해 정렬할 수 있지만 query result 배열·mutation 순서·stream 메시지는 임의 정렬하지 않는다.

동적으로 할당되는 ID·transaction ID·cursor token은 실제 값 동일성 대신 각 실행 내 참조 일관성과 후속 동작을 검사한다. hardcoded masking으로 모든 token을 같은 값으로 바꾸지 않는다. 질의에는 명시적 order와 tie-breaker를 설정해 실제 순서 차이를 숨기지 않는다.

### 18.4 시간·네트워크·무작위성

unit 상태기계는 가짜 clock과 수동 완료 가능한 auth/fetch/read Promise로 제어한다. 불필요한 sleep으로 경합을 재현하지 않는다. frame 분할 property test는 고정 seed와 실패 seed를 기록한다. 동일 microtask에서 cancel/EOF가 경쟁하는 양쪽 순서를 각각 직접 실행한다.

배포 E2E는 wall-clock jitter를 고려해 timeout의 정확한 milliseconds를 assert하지 않는다. status·최대 시도수·추가 데이터 없음·정리 완료를 우선 검증하고 시간은 허용창으로 보조 검증한다. Worker 내부 시간 API의 실행 특성을 고려해 CPU-only microbenchmark를 단순 Date.now 차이로 측정하지 않는다. [S22]

## 19. 설치·타입·API 호환성 시험

### 19.1 설치 graph

real tarball을 임시 registry에 올린 뒤 root alias-only negative fixture와 alias+override positive fixture를 각각 새 디렉터리에 설치한다. nested GAX가 두 버전 경로를 갖는 fixture도 포함한다. consumer root·GAX 파일 위치·SDK 위치 각각에서 resolved file과 실제 package version을 출력한다.

`npm ci` 재현, lockfile에 원본 grpc-js transport가 남는지, package export 경로에 없는 파일을 기대하는지, root package.json과 deep client import를 확인한다. symlink 제거 후에도 작동해야 한다. 교체 패키지를 자기 이름과 alias 이름으로 이중 설치해 두 class가 생기는 잘못된 recipe는 doctor가 탐지한다.

### 19.2 타입·module identity

TypeScript strict + skipLibCheck=false에서 Node16/NodeNext/bundler moduleResolution을 지원 행렬에 명시한다. 앱 ESM import와 GAX CJS require가 같은 Metadata/Client/credentials constructor를 보아야 한다. buffer metadata의 instanceof와 compose, root vs deep path identity를 실제 코드로 검사한다.

generated client overload, callback nullable error, readable object stream 타입, SDK Promise tuple, Datastore.Key·Transaction·Query 타입을 소비자 소스에서 확인한다. 타입-only root exports 때문에 원본 HTTP2 runtime을 끌고 들어오면 실패다. API snapshot diff에는 추가 허용·삭제·signature 변경을 분리한다.

### 19.3 Client·factory·interceptors

직접 `new Client`, `extends Client`, `makeGenericClientConstructor`, `loadPackageDefinition`이 같은 transport 경로인지 계측한다. service metadata·originalName alias·protobuf definition 객체를 비교한다.

인터셉터가 request/metadata/deadline을 바꾸거나 error/cancel을 발생시키는 경우, final CallContext가 변경 후 값을 받아야 한다. user invocation transformer와 동시에 사용한 순서를 native trace와 비교한다. unsupported client streaming/bidi도 public 반환 surface를 통해 error를 받으며 fetch/auth 0회여야 한다.

## 20. Datastore 기능별 시험 계획

### 20.1 fixture dataset

각 실행에 격리된 namespace와 run prefix를 사용한다. namespace 기능이 사용 불가한 환경에는 별도 테스트 프로젝트/명시적 key prefix 정책을 둔다. 운영 namespace는 사용하지 않는다. 엔티티 종류는 simple, typed, ancestor, paged, transaction으로 작게 나눈다.

값 집합: 짧은 문자열/빈 문자열/Unicode, bool, null, 정수·큰 int64, double, Date, bytes, 배열, 중첩 객체, GeoPoint 등 선택 SDK의 명시적으로 지원한 값, excludeFromIndexes, 불완전 key. 큰 entity/server limit는 Google 제품의 제약을 어댑터 버퍼 한도와 혼동하지 않는다.

### 20.2 기능 매트릭스

| 영역 | 실제 SDK 경로 | 필수 oracle |
|---|---|---|
| 저장 | save/insert/update/upsert | Commit mutation 종류, single/batch, 불완전 key 결과 반영 |
| 조회 | get(key)/get(keys) | found/missing/deferred, scalar/array 형태, SDK가 보장한 정렬 의미 |
| 삭제 | delete(single/batch) | Commit delete, 이미 없는 key의 의미 |
| ID | allocateIds 및 실제 타입에 있는 reserve 경로 | 고정 API의 결과 형태·정밀도 |
| Query | createQuery/runQuery | filter/order/limit/offset/cursor/select/ancestor/namespace |
| 페이지 | 작은 pageSize·start/end cursor | 모든 결과 정확히 한 번, 다음 페이지 요청 조건 |
| 집계 | 해당 SDK의 count/sum/avg 경로 | RunAggregationQuery의 타입·빈 집계 결과 |
| query object stream | runQueryStream | data/info/error/end, pause/resume, destroy 후 새 페이지 요청 금지 |
| read object stream | createReadStream | Lookup deferred 재조회·오류·부분 결과 |
| 오류 | 권한/잘못된 query/필수 index | code/details/metadata의 native 의미 |
| 인증·routing | project/database/namespace/credentials | x-goog-request-params 등 의미와 토큰 scope |
| API 형태 | callback와 Promise | tuple 위치·개수·response info·error 위치 |

SDK에 존재하는 메서드·옵션명은 설치한 d.ts에서 확인한 것만 fixture에 사용한다. data proto에 RPC가 있다는 이유로 `datastore.reserveIds()` 같은 고수준 함수를 추측하지 않는다. source branch의 aggregate 지원을 실제 배포본 지원이라고 표시하지 않는다.

### 20.3 Transaction 상세 시나리오

| 시나리오 | 기대되는 계약 |
|---|---|
| 시작→get→update→commit | 동일 transaction ID와 mutation, 성공 반환 형태 |
| 시작→query→commit | query의 transaction option 전달·결과 |
| 시작→save→rollback | commit 없음, rollback ID 일치, 서버에 저장 결과 없음 |
| read-only transaction | 원본 SDK가 허용/거부하는 쓰기 의미 보존 |
| conflict / ABORTED | native 코드 보존. adapter가 transaction 전체를 새로 수행하지 않음 |
| Commit 이전 network failure | 실패와 시도수 기록, 동일 Call 재송신 0 |
| Commit 적용 후 response loss | mutation 한 번, 불확실한 오류, 성공/rollback 조작 없음 |
| Commit 도중 사용자 cancel | 로컬 cancel; 서버 mutation rollback 보장 없음 |
| transaction 두 개 동시 실행 | ID·credentials·buffer 섞임 없음 |
| callback/Promise 에러 | code/details/tuple 또는 callback args 일치 |

통제된 서버에서는 retry를 끈 동일 test-case 옵션을 두 소비자에 주어 adapter 중복 실행만 분리한다. SDK retry 시험은 별도의 동일 코드 fixture에서 의도적으로 상위 retry를 켠다. 테스트 편의를 위해 Worker 쪽 business 함수만 다른 옵션을 쓰지 않는다.

### 20.4 실제 Google E2E의 범위

현실적으로 강제하기 어려운 deferred Lookup, 특정 chunk 경계, Commit 반영 후 연결 유실은 통제된 서버 시험이다. 실제 Google E2E는 기본 CRUD·typed value·query/cursor·aggregation·정상 transaction/rollback·permission error·인증 경로를 확인한다. 두 부류를 합쳐 "Google에서 모든 fault injection 검증"이라고 쓰지 않는다.

테스트 리소스 생성·삭제는 전용 project에 제한한다. run prefix 기반 cleanup은 finally에서 수행하고 실패한 cleanup을 별도 보고한다. 테스트 권한 부족을 제품 버그와 구별하지만 required E2E를 skipped로 끝내면 출시 인증은 받지 못한다.

## 21. Wire·lifecycle·security·성능 시험

### 21.1 Wire 필수 경계

5바이트 header의 1/2/3/4 경계 분할, 작은 frame을 1바이트씩 수신, 한 chunk에 data+trailer, payload/trailer 중간 분할, zero-length message, max−1/max/max+1, 0xffffffff, reserved bit, compressed frame, 중복 trailer, trailing data, missing status, trailers-only, HTTP200+non-OK, malformed UTF-8 percent/base64를 검사한다.

작은 frame은 모든 분할을, 큰 frame은 경계+seeded 분할을 사용한다. 큰 입력의 모든 byte 조합을 전수 조사하는 비효율적인 시험을 요구하지 않는다. semantic payload는 별도 decoder/native server로 확인하고 synthetic frame vector 검사는 wire 구조에만 한정한다.

### 21.2 lifecycle·종료 경쟁

start 전 cancel, auth 중 deadline, write ack 전 cancel, halfClose/auth 완료 순서의 양쪽, fetch resolve와 cancel 동시, partial response 뒤 channel close, trailer 후 EOF 전 cancel, 정상 완료 뒤 늦은 auth reject, listener reentry, callback throw, 두 Call 독립 취소를 각각 시험한다.

모든 경로에서 final delivery count·data fetch count·write callback count·active call count·buffer ownership·timer/pump 수를 확인한다. 위 불변식 중 하나라도 깨지면 API 정상 결과가 나왔어도 실패다.

### 21.3 Backpressure와 자원 상한

느린 소비자에게 1KiB 메시지 다수를 보내 pause 시 pending≤1, assembly≤1인지 계측한다. 이후 resume 순서·end 전달과 destroy/cancel 정리를 확인한다. stream 총합이 개별 메시지 safety cap보다 커도 전체 버퍼링 없이 처리해야 한다.

adapter 소유 메모리 회계에는 request clone과 framed request가 동시에 존재하는 구간, response pending/assembly, header/trailer buffers를 모두 포함한다. runtime 현재 chunk와 upstream decoded object는 별도 항목으로 측정한다. "heap 전체가 2×message cap 이하" 같은 잘못된 보장을 하지 않는다.

### 21.4 성능 측정·회귀 정책

기록할 값은 transport-only 번들, SDK 포함 bundle, gzip 크기, cold import·initialize, unary p50/p95, first-message latency, codec 처리량, 소유 buffer high-water, 완료 후 retained resources다. 첫 측정은 baseline 생성이며 그 이전에는 수치 성능 우위를 주장하지 않는다.

결정적 회귀 gate는 완료 후 retained resources=0, fetch duplication=0, byte/callback/event 의미 위반=0이다. bundle/CPU/latency는 동일 환경 baseline 후 임계값을 프로파일에 숫자로 고정한다. 아직 미측정인 threshold는 null이며 release 성능 인증은 blocked다. 네트워크 지역이 다른 두 측정을 codec 최적화의 효과로 비교하지 않는다.

### 21.5 보안 negative tests

HTTPS downgrade, redirect target의 bearer 수신, custom CA/mTLS 무시, unknown target fallback, encoded method path escape, duplicate authorization, CRLF injection, malformed huge lengths, mixed credentials parallel requests, secret in log/artifact를 시험한다. insecure local fixture는 실제 Google credentials가 없음을 assert한다. static build는 unknown schema/version에서 실패하고 프로필 범위를 벗어난 앱 protobuf를 변경하지 않아야 한다.

## 22. CI 명령·증거·출시 gate

### 22.1 제안 명령 계약

아래 script/CLI는 **구현 예정 명령**이다. 동봉 문서 검증 스크립트를 제외하고 현재 실행되지 않았다. **예상 결과:** 각 명령은 해당 계층만 실행하고 구조화 결과를 생성한다.

```text
npm run test:packaging     # registry/tarball/alias/npm ci/resolve
npm run test:types         # 실제 SDK + root/deep declarations
npm run test:unit          # wire/config/auth/call/options
npm run test:workers       # 실제 workerd import·bootstrap·call
npm run test:interop       # native server + Envoy differential
npm run test:datastore     # 공유 business module + 통제된 data service
npm run test:e2e:cloud     # 보호된 환경의 배포 Worker + Google
npm run test:docs          # fixture 기반 문서 예제 compile
npm run check:release     # manifest·required case·증거·license 확인
```

fork PR에는 cloud secret을 주입하지 않는다. local tests와 deployment workflows를 분리한다. cloud E2E는 protected branch/release candidate에서 실행하고 CI identity·테스트 project allowlist를 검사한다.

### 22.2 구현 gate

| gate | 완료 기준 | 실패 시 처리 |
|---|---|---|
| G0-PACK | 실제 tarball alias·all GAX resolution·exports·타입 identity | runtime 구현 확대 전에 packaging 수정 |
| G0-BOOT | 실제 workerd에서 SDK import→첫 serialize/deserialize, 필요한 build profile | 파일/codegen 원인과 한정 프리셋 확정 |
| G1-CORE | wire/auth/state machine/오류/취소 unit, 직접 grpc-js API | core 출시 불가 |
| G2-SDK | 동일 Datastore business의 controlled CRUD/query/transaction/stream | drop-in 표기 불가 |
| G3-INTEROP | native gRPC 서버와 Envoy differential, 재시도·fault injection | grpc-web 상호운용 인증 불가 |
| G4-CLOUD | 배포 Worker 변환 + Datastore Google E2E + Secret Manager 회귀 | Cloudflare/Google 지원 표기 불가 |
| G5-RELEASE | exact pin·증거·문서·라이선스·성능 baseline·tarball 검사 | stable/release 후보 발행 금지 |

G0-BOOT의 제한된 fake response 성공은 auth E2E가 아니다. G3는 G4의 대체가 아니다. G4 실행 환경이 없으면 개발은 계속할 수 있으나 해당 프로파일은 `blocked`이고 cloud 인증 완료로 발행하지 않는다.

## 23. 버전·프로파일·호환 선언

### 23.1 exact profile

`compatibility/manifest.template.json`에 replacement version, grpc-js upstream npm version/commit/integrity, Datastore/GAX/auth/proto-loader/protobufjs의 실제 resolved version, TypeScript, Node/npm, Wrangler/workerd/Miniflare/Vitest/Envoy, compatibility_date·flags, gateway/Cloudflare 경로, 인증 방식, schema profile hash를 기록한다.

`latest`, `^x.y`, "Node 호환 런타임 전체"는 인증 key로 사용하지 않는다. 처음에는 **Datastore 후보 한 버전 + 해당 lockfile + Workers 한 프로파일 + native 기준 환경**만 필수로 잡는다. 다른 SDK/런타임/패키지 매니저는 동일 핵심 suite로 확대한다. 무제한 Cartesian 조합을 첫 버전에 요구하지 않는다.

### 23.2 상태 값

| 상태 | 의미 |
|---|---|
| planned | 설계에 포함, 실행 전 |
| source-reviewed | 코드 검토만 완료 |
| locally-verified | 지정 local 계층 통과 |
| workers-verified | 실제 workerd 계층 통과 |
| cloud-certified | 필수 deployed E2E 및 release gate 통과 |
| blocked | 환경/기능/의존 버전 문제로 required 실행 불가 |
| unsupported | 의도적으로 범위 밖 |

현재 모든 제품 프로파일은 planned/source-reviewed다. 동봉 타입 계약 검사 성공은 이를 workers-verified로 올리지 않는다. 어떤 SDK 메서드가 local만 통과했는지, 어떤 인증 방식이 실제 Google에서 통과했는지를 분리한다.

### 23.3 의존성 업그레이드 절차

upstream 보안/버그 수정은 vendor diff를 검토하고 patch 재적용·source hash·API snapshot·generated client fixture·auth·event trace·Datastore suite를 재실행한다. GAX가 새 option/deep import를 추가하면 strict 실패를 발견하여 지원/거부 정책을 명시한다. 변환 profile의 source hash 불일치를 자동 무시하지 않는다.

기존 호환 인증은 새로운 dependency 조합으로 자동 승계하지 않는다. 정확한 버전에만 핀된 인증을 넓은 semver 지원으로 확대할 때는 경계 버전과 해당 변경 경로 테스트를 추가한다.

## 25. 이 개정에서 제공한 자산·실제 검증 상태

동봉 자산은 상세 명세, 요구사항 목록, 테스트 카탈로그, 호환 manifest 템플릿, 제안 config/build d.ts, 타입 계약 시험, synthetic wire fixture, 설계 자산 검사 스크립트다. **라이브러리 구현 코드나 실제 SDK 호환 테스트 결과가 아니다.**

실제로 실행한 항목과 결과는 `verification/report.json`에 기록한다. 검사 범위는 다음으로 한정한다.

- 제안 확장 d.ts와 positive/negative TypeScript 사용 예시의 strict typecheck.
- JSON 유효성, 요구사항/테스트 ID 중복·참조, planned status와 실행 결과의 혼동 방지.
- synthetic frame 예제의 독립적인 길이/flags/trailer 구조 검사.
- 문서·카탈로그·bundle 파일 존재 및 참조 일관성.

설계의 runtime 입력 validation, 상태기계, 실제 npm alias 설치, Datastore import·첫 요청, Google 인증, Cloudflare 변환, bytes streaming은 **이번 개정에서 실행하지 않았다**. 외부 npm/소스 패키지를 container에서 가져와 실제 SDK를 설치하는 검증도 하지 않았다. v0.2의 모의 alias 결과는 해당 버전의 별도 artifact에만 있으며 여기서 새로 통과했다고 보고하지 않는다.

### 부록 A. 개발 시작 순서

첫 구현 PR은 **실제 tarball 설치 + 최소 facade + credentials + 실제 SDK bootstrap 증거**에 집중한다. 큰 wire parser를 먼저 만든 뒤 import/codegen 문제를 뒤늦게 발견하지 않는다. 두 번째 단계에서 직접 unary 성공·non-OK·auth·deadline을 연결하고, 그다음 bounded server streaming·Datastore object stream·transaction differential을 완성한다. 마지막으로 실제 Cloudflare/Google E2E와 문서·호환 인증을 통과시킨다.

어떤 단계도 사용자에게 각 SDK의 코드를 고치라고 요구하는 방식으로 drop-in 목표를 낮추지 않는다. 다만 pin하지 않은 버전이나 테스트하지 않은 런타임까지 지원된다고 확대하지 않는다.
