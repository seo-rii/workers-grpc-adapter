# Temporary Cloud Run upstreams

This fixture supplies a fixed Envoy configuration for an isolated cloud test. It
does not deploy resources, read credentials, enable APIs, or change IAM policy.
The [image manifest](images.json) pins public Linux AMD64 images by digest, so
deployment does not require a custom build, Artifact Registry repository, source
archive, or Cloud Build job.

Use two new services with independently checked unique names:

| Service | Image | Container port | Purpose |
| --- | --- | --- | --- |
| Native | Pinned `moul/grpcbin` | `9000`, named `h2c` | Controlled native gRPC unary, server streaming, and non-OK status |
| Gateway | Pinned `envoyproxy/envoy` | `8080`, named `h2c` | Explicit gRPC-Web translation to the native service and fixed Google APIs |

Keep both services private with the Cloud Run Invoker IAM check enabled. Use
minimum instances `0`, maximum instances `1`, concurrency `4`, a `30s` request
timeout, `1` CPU, `512Mi` memory, and request-based CPU allocation. Cloud Run
terminates TLS; both containers receive cleartext HTTP/2. Do not configure a
custom domain, VPC connector, persistent storage, trigger, or project-level IAM
binding for this test.

Generate the gateway configuration after obtaining the newly created native
service's URL:

```js
const { createEnvoyConfig } = require('./fixtures/cloud-run-probe/envoy-config.cjs');
const config = createEnvoyConfig({ nativeOrigin: nativeServiceUrl });
// Container command: /usr/local/bin/envoy
// Container arguments: --config-yaml, JSON.stringify(config), --concurrency, 1,
//                      --log-level, warning
```

The native upstream is optional when only Google API tests are needed. The
generator accepts only an HTTPS `*.run.app` origin for it. There is no dynamic
forward proxy: only POST requests under the Secret Manager, Firestore, Datastore,
and optional grpcbin service paths are routed. Unknown routes return `404`.
Routes time out after `25s`, upstream connections use HTTP/2 with certificate and
hostname verification, and no retry policy is configured. There is no admin
listener or request/header access logging.

For a local syntax check, pass `JSON.stringify(config)` to the repository's
pinned Envoy binary using `--mode validate --config-yaml`; do not interpolate
JSON into shell command text.

## Authentication

Use short-lived tokens in memory or Worker secret bindings. Never put them in
the Envoy configuration, image, service command arguments, or report.

| Call | `X-Serverless-Authorization` | `Authorization` | `X-Wga-Upstream-Authorization` |
| --- | --- | --- | --- |
| Client → native Cloud Run | Native service ID token | Unused | Unused |
| Client → gateway → native Cloud Run | Gateway service ID token | Unused | Native service ID token |
| Client → gateway → Google API | Gateway service ID token | Google OAuth access token | Unused |

Cloud Run authenticates `X-Serverless-Authorization` when both headers are
present. Envoy removes it before forwarding. On the native route only, Envoy
copies the opaque `X-Wga-Upstream-Authorization` value to `Authorization`, then
removes the opaque header. This avoids relying on an ID token in a recognized
authorization header surviving authentication at the gateway hop. Google routes
preserve their OAuth `Authorization` and also remove the opaque header if sent.
The explicit route-to-global mutation order ensures copying happens before
removal. A user identity token generated by `gcloud auth
print-identity-token` is suitable for developer tests when that user can invoke
the services. Service account ID tokens must have the receiving service's URL as
their audience. No service account key needs to be created for this fixture.

Use the native service for a positive native gRPC control and a negative direct
gRPC-Web control. A Cloudflare automatic-conversion claim additionally requires
the adapter's `cloudflare` mode to succeed against that same native service. A
successful call through the gateway only establishes explicit fallback support.

## Collision prevention and cleanup

Before creation, inventory the selected project's services and check that each
exact generated name is absent in the selected region. Prefer Cloud Run's create
API, which rejects an existing service, over an unchecked deploy/upsert. Record
each created service's full resource name and UID before proceeding. Existing
services, API enablement, IAM policies, databases, secrets, and images remain
outside this fixture's creation/deletion set.

In a `finally` cleanup path, delete only the services created by the run after
checking their UIDs still match. Wait for deletion and confirm each exact
resource returns `NOT_FOUND`. Delete the temporary Cloudflare Worker and its
secret bindings, plus any separately created Google test data/resources. A
partial deployment failure still requires cleanup of already-created services.
No custom image or build artifact is created by this public-image approach;
normal provider audit and request records can remain after service deletion.
